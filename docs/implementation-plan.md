# Implementation Plan

Companion to [decisions.md](decisions.md) — this is the concrete shape of the app before any
scaffolding code is written.

## Repo structure

```
ai-interviewer/
  backend/
    pyproject.toml            # uv project
    app/
      cli.py                   # terminal entry point — built and tested FIRST
      main.py                  # FastAPI app, CORS, router mounting — built LATER, if time allows
      config.py                # env-driven settings (LLM_PROVIDER, DB path, etc.)
      db.py                    # SQLAlchemy engine/session
      models.py                # SQLAlchemy ORM models
      schemas.py                # Pydantic request/response models
      routes/
        interviews.py          # /interviews endpoints (phase 2)
      providers/
        base.py                # Provider abstract interface (strategy pattern)
        claude_provider.py
        gemini_provider.py
        openai_provider.py
        mock_provider.py
      services/
        orchestrator.py         # interview loop / checklist state machine (fat service layer)
        analysis.py              # summary + bonus keyword/sentiment analysis
        export.py                 # JSON + PDF export, shared by CLI and API
      prompts/
        interviewer.md
        analyst.md
    tests/
  frontend/
    (Vue + Vite scaffold — phase 2, only if time remains)
  docs/
    decisions.md
    implementation-plan.md
    external/
  prompt_lab/                 # already built, standalone
```

Key point: `cli.py` and `main.py` are two thin entry points over the *same* `services/` and
`providers/` layer — the orchestrator doesn't know or care whether it's being driven by
`input()`/`print()` in a terminal or by FastAPI request/response. That's what makes "terminal
first, web later if time allows" safe: nothing in phase 2 rewrites phase 1, it only adds a
second entry point.

## Database schema (SQLite via SQLAlchemy)

```
interviews
  id            INTEGER PK
  topic         TEXT
  status        TEXT        -- "in_progress" | "completed"
  checklist     JSON        -- current checklist state, list of {id, text, covered}
  created_at    DATETIME
  completed_at  DATETIME NULL

turns
  id            INTEGER PK
  interview_id  INTEGER FK -> interviews.id
  turn_index    INTEGER
  question      TEXT
  answer        TEXT NULL   -- null until user responds
  created_at    DATETIME

summaries
  id                INTEGER PK
  interview_id      INTEGER FK -> interviews.id (unique, 1:1)
  themes            JSON      -- [{name, sentiment, quote}]
  key_points        JSON      -- [string]
  keyword_extract   JSON      -- bonus: [string] top keywords
  sentiment_score   FLOAT NULL -- bonus: lexicon-based overall score
  created_at        DATETIME
```

Rationale: `checklist` as JSON on `interviews` (not a separate table) because it's small,
always read/written as a whole unit, and SQLite's JSON1 support makes this simple without
over-normalizing a 3-5 item list.

SQLite is the durable store for *running* an interview across process turns, but it's not the
deliverable — the assignment asks to "store the interview transcript and summary in a simple
format (JSON, text file, or database)." So every completed interview also gets exported:

- **JSON export** (required, satisfies the spec directly) — `exports/{interview_id}.json`, full
  transcript + summary, one file per interview, human-readable and diffable.
- **PDF export** (extra polish, not in the spec but a nice differentiator) — `exports/{interview_id}.pdf`,
  a simple rendered report: topic, Q&A transcript, themes/sentiment/key points. Use `fpdf2`
  (lightweight, pure-Python, no system dependency like a headless browser) — not worth pulling
  in a heavier PDF/HTML-rendering stack for a one-page report.

Both exports are generated by one `services/export.py` module, called right after the summary
is produced (CLI mode: automatically at the end of the run; API mode: on-demand via the summary
endpoint or a dedicated `/interviews/{id}/export` route later).

## API contract (phase 2 — only built after the CLI works and is tested)

```
POST   /interviews                 { topic }                    -> { interview_id, question }
                                    creates interview, seeds checklist, returns first question

POST   /interviews/{id}/answer     { answer }                   -> { question, done }
                                    persists answer to current turn, advances loop,
                                    returns next question OR done=true if checklist covered

GET    /interviews/{id}/summary                                 -> { themes, key_points,
                                                                      keyword_extract, sentiment_score }
                                    triggers analysis on first call if not already run, persists it,
                                    also triggers JSON + PDF export to disk

GET    /interviews/{id}                                         -> full transcript + status
                                    (for the transcript view / debugging)
```

Kept deliberately small — 4 endpoints, matches the 5-step flow from the assignment spec.

## CLI contract (phase 1 — build and test this first)

```
uv run interview
```

Interactive terminal flow: prompt for topic -> print each question, read answer via `input()`,
show a brief "thinking..." indicator while the provider call is in flight -> print final
summary (themes/sentiment/key points + bonus keyword/sentiment) -> write
`exports/{interview_id}.json` and `exports/{interview_id}.pdf` -> print the export paths so the
user knows where to find them.

## Provider interface (strategy pattern)

```python
class LLMProvider(ABC):
    def next_turn(self, topic: str, checklist: list[dict], history: list[dict]) -> InterviewTurnResult:
        """Returns {checklist: [...], next_question: str | None, done: bool}"""

    def analyze(self, topic: str, history: list[dict]) -> AnalysisResult:
        """Returns {themes: [...], key_points: [...]}"""
```

Both methods map directly to the two system prompts (interviewer, analyst) and the two
structured tool schemas already validated in `prompt_lab/`. `MockProvider` implements the same
interface with canned/deterministic responses — no network call, used for local dev/demo and
tests.

## Turn bounds: floor and cap

The assignment requires "3-5 sequential AI-generated interview questions" — the checklist loop
alone doesn't guarantee that, since the model could set `done=true` after 1-2 turns if it
judges the checklist covered early. The orchestrator enforces both ends:

- **Floor = 3**: `done=true` from the provider is ignored (loop continues) until at least 3
  turns have completed, regardless of checklist state.
- **Cap = 8**: hard stop regardless of checklist state, to bound cost/latency. If hit before
  `done=true`, the orchestrator force-ends the interview (`status=completed` with whatever
  checklist coverage was reached) rather than erroring.

This floor/cap check lives in the orchestrator, not in the provider/prompt — the model should
never need to know about it, it's a backend invariant.

## Provider error handling

If a provider call fails (network error, rate limit, timeout) mid-interview: **retry once with
a brief fixed backoff (~2s), then fail loudly** — print a clear error to the terminal and exit
non-zero. The interview row stays `status=in_progress` in SQLite; resuming an interrupted
interview is out of scope for MVP. Explicitly not falling back to `MockProvider` on failure —
that would silently mask real provider bugs during grading/demo, which is worse than a visible
failure.

## Model IDs (env-configurable, not hardcoded in provider code)

```
CLAUDE_MODEL=claude-sonnet-5
GEMINI_MODEL=gemini-2.5-flash
OPENAI_MODEL=gpt-5.6
```

Each provider reads its model id from env with the above as default, per `docs/external/*.md`.

## Empty/low-effort CLI answers

If the user submits an empty answer (just presses Enter), the CLI treats it the same as any
other low-effort answer — passed through to the provider as `""`, which the interviewer
prompt's existing low-effort-nudge rule already covers (ask once for something concrete, then
move on regardless). No special-casing needed in the CLI layer itself.

## Shipped prompt default

`prompt_lab` produced two untested interviewer variants (`interviewer_v1`, `interviewer_v2`)
and one analyst variant (`analyst_v1`). Since prompt grading is deprioritized for now, the
backend ships with **`interviewer_v1` + `analyst_v1`** as the default (`backend/app/prompts/`),
swappable later once `prompt_lab/results/scores.csv` has real grades.

## Frontend (Vue + Vite)

Three views, one flow, no routing complexity beyond that:
1. **Topic entry** — text input, "Start interview" button -> `POST /interviews`
2. **Interview** — shows current question, text input for answer, submit -> `POST /interviews/{id}/answer`, loops until `done`. Shows a visible "thinking..." state while waiting on the backend (UX requirement from decisions.md).
3. **Summary** — themes + sentiment + key points + bonus keyword/sentiment display, fetched from `GET /interviews/{id}/summary`.

Vue Router with 3 routes (`/`, `/interview/:id`, `/interview/:id/summary`) rather than manual
component swapping — small enough to hand-roll, but Router keeps URLs shareable/refreshable.

## Build order

**Phase 1 — terminal tool (the actual MVP; assignment explicitly allows terminal UI)**

1. Backend skeleton: `uv init`, SQLAlchemy models + `create_all`, `MockProvider`
2. Orchestrator service (checklist state machine) driven end-to-end by `cli.py` against
   `MockProvider` — prove the loop logic without spending on real API calls
3. JSON + PDF export module, wired to run at the end of every CLI interview
4. Swap in the real provider (Claude first, since it's the assignment's namesake), test the full
   terminal flow for real, then add Gemini/OpenAI using the interfaces already validated
   conceptually in `prompt_lab/`
5. Bonus analysis (lexicon sentiment + keyword extraction) layered onto the summary step, per
   the "polish over breadth" priority
6. **Test thoroughly** — this is the deliverable if time runs out, so it needs to be genuinely
   polished on its own before phase 2 starts

**Phase 2 — web frontend (only if time remains after phase 1 is solid)**

7. FastAPI routes as a second entry point over the same `services/`/`providers/` layer
8. Vue + Vite frontend: topic entry -> interview loop -> summary, wired to the 4 endpoints
